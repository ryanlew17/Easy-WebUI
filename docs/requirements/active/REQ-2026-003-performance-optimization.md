# REQ-2026-003：安全修复后的性能评估与深度优化

状态：active（独立排期，不阻塞 REQ-2026-002 / v1.0.3）
来源：REQ-2026-001 至 REQ-2026-002 修复、遗留事项与 2026-11-01 综合性能评估
关联设计：`design/security.md`、`design/chat.md`、`design/message-tree.md`、`design/storage.md`、`design/ux-guidelines.md`、`design/ui-liquid-glass.md`
影响模块：`electron/crypto/`、`electron/backup/`、`electron/db/`、`electron/gateway/`、`src/store/`、`src/components/`、`src/pages/chat/`、构建配置、`scripts/` 与 `tests/`
非目标：降低安全上限或放松校验；长期缓存 API 密钥明文；更换数据库或 UI 框架；无测量依据的虚拟滚动/多线程改造；PRD 已排除的功能

## 背景

REQ-2026-001 的异步 safeStorage、响应大小限制、错误脱敏、消息树防环和备份防护，以及 REQ-2026-002 的输入上限、协议错误收口和富文本摘要，都必须在保留安全语义的前提下评估成本。性能优化只消除重复解密、重复渲染、N+1 查询和可避免的阻塞，不以撤销安全修复换取速度。

当前证据来自静态代码核查、现有构建产物和命令基线；尚无足够运行期数据支持“某项修复造成具体百分比回退”的结论。REQ-2026-003 因此先建立可复现基准，再按测量结果实施低风险优化和结构性改造。

## 性能损失与待办评估

| 领域 | 当前判断 | 优化边界 |
| --- | --- | --- |
| safeStorage 异步化 | 每次解密跨越异步边界是必要适配；`shouldReEncrypt=true` 后不回写导致后续持续双解密，是明确的可消除成本 | 首次成功解密后重加密并回写；失败不阻断本次调用，不引入明文缓存 |
| 响应/SSE/错误限制 | 累计长度、事件上限和错误截断增加常数或线性成本，属于安全预算；超长 token 估算兜底避免了病态输入的超线性退化 | 不降低 16MB/1MB/4M 字符、2000 字符错误截断和 20 万字符 token 兜底等现有限制 |
| 消息树防环 | `visited` 集合是必要的线性成本；`unshift`、逐节点 SQL 和重复全量索引会放大大会话开销 | 保留防环和分支不变量，改为线性数组操作、共享索引与批量访问 |
| 备份防护 | manifest/条目尺寸检查相对 I/O 成本很小，但同步 ZIP、JSON、文件操作仍可能阻塞主进程 | 保留 256MB 条目上限、路径白名单、KDF 和密钥导出规则；优化缓存与任务调度 |
| 流式渲染 | 50ms 节流已存在；每次 flush 仍扫描所有已加载会话，并重复渲染可见气泡、Markdown 和代码高亮 | 定向更新受影响会话，稳定引用与记忆化，延迟不必要的流式高亮 |
| 首屏加载 | Markdown、GFM、DOMPurify 和全部已注册高亮语言进入单一主包 | 设置页、升级摘要和高亮语言按需加载，保持 Electron `file://` 可用 |
| zod 与协议收口 | schema 上限防止内存放大；错误规范化是必要成本；zod 4 已观察到主包体积增加，运行期收益仍需测量 | 不删除 IPC 校验或 models ≤2000；复用模块级 schema，并评估通道常量与 schema 拆分 |
| 升级摘要富文本 | 仅在发现更新并展示时增加一次 Markdown/HTML 解析与消毒，不应影响常规聊天首屏 | 使用白名单和按需加载，不为聊天消息开启 raw HTML |

## 分阶段优化方案

### 阶段 1：建立可复现性能基准

- 主进程使用 `node:perf_hooks`，渲染进程使用 Performance API 与现有 Puppeteer 脚本采集数据；默认不新增性能依赖。
- 建立代表性数据集：1 万条含分支消息、50 条可见气泡、长 Markdown/多代码块流式内容、批量模型检测、大量备份 manifest，以及 `shouldReEncrypt=true` 的旧密文。
- 记录冷启动可交互时间、`listMessages` 与分支/删除操作 p50/p95、20Hz flush 的脚本耗时和长任务、首屏包体、内存峰值、备份各阶段阻塞时间，以及 typecheck/build/test 时间。
- 将测量脚本放在现有 `scripts/` 体系，可重复执行且不写入业务数据目录；基准数据与结果仅保留任务所需文件。

### 阶段 2：低风险、可独立验证的优化

- **密钥重加密回写**：通过受控写路径在成功取得新解密串后更新密文；验证首次回写后不再重复双解密、回写失败不影响解密、旧密文兼容和机器密文导出禁令。
- **流式状态定向更新**：pending buffer 携带 conversationId，仅更新受影响会话和消息，避免遍历所有已加载会话；保持 done/error 前 flush 与消息树语义。
- **渲染记忆化**：在回调引用稳定的前提下 memo 化 `MessageBubble`、`Markdown` 和代码块；减少 `visible`、尾部 assistant 等重复派生计算。
- **流式高亮降级**：生成期间优先处理已闭合代码块，未完成代码块保留纯文本，完成后执行最终高亮；不得改变正文、复制内容或 DOMPurify 消毒链路。
- **按需加载**：升级摘要异步拆包已在 REQ-2026-002 阶段 5 完成；继续评估设置页和高亮语言拆分，记录主包与异步包前后体积，并验证开发、Web 预览和打包 `file://` 加载。
- **线性路径构造**：将路径反转由反复 `unshift` 改为 `push + reverse`，保持父缺失和成环截断行为。

### 阶段 3：主进程与数据层结构优化

- **消息树共享索引**：评估 list/path/subtree/delete 共用索引与批量遍历，消除 N+1 SQL；任何分支操作、删除和激活路径恢复必须通过现有及新增回归测试，并同步 mock 行为。
- **索引按证据调整**：先用 `EXPLAIN QUERY PLAN` 和基准确认瓶颈，再决定是否新增 `(conversation_id, parent_id, created_at)` 等复合索引及 schema 迁移，不预设迁移必需。
- **备份 manifest 缓存**：按文件名、尺寸和修改时间失效，避免设置页重复打开时反复解压同一批 manifest；损坏或超限文件不得被缓存为可信数据。
- **ZIP/JSON 阻塞治理**：若基准显示明显长任务，将压缩/解压和 JSON 阶段移至 worker；SQLite 事务保持原子，worker 只接收必要数据，不扩大明文密钥生命周期、日志或导出边界。
- **token 与网关路径**：确认缓存的 `token_count` 被有效复用；只有 profile 证明计数/裁剪是主要热点时才调整算法，保留病态输入兜底和全部协议限制。

### 阶段 4：按测量决定消息虚拟化

分页、定向更新和记忆化仍无法达到预算时，才引入可变高度消息虚拟化或 `content-visibility` 等渐进方案。必须保留加载更早、分支切换、批量选择、编辑、贴底跟随、用户上翻不被打扰、焦点和可访问性；不得为虚拟化改变消息树事实来源。

## 验收标准

- 基准脚本可重复运行，优化前后数据包含 commit、环境、数据集、p50/p95、长任务和必要的内存指标；未实测项目明确标注，不宣称估算收益。
- 冷启动 <3s、流式 50ms 节流和 1 万条消息首屏 <500ms 的既有目标得到验证；若环境无法支撑目标，记录阻塞原因和下一项可执行优化，不修改口径掩盖回退。
- safeStorage 回写后，同一旧密文不再在每次使用中重复双解密；回写失败非致命，无明文密钥持久缓存。
- 流式 flush 不再扫描无关会话，未变化气泡不重复执行 Markdown/高亮；首屏拆包后功能与 `file://` 加载正常。
- 消息树遍历、删除和分支恢复保持其他分支可达及激活路径存活不变量，`tests/db-messages.test.ts` 必须全绿。
- 备份优化保留全部尺寸、路径、加密和导出不变量；同步 ZIP/JSON 的阻塞改善有测量证据。
- 安全响应上限、token 超长兜底、IPC schema、错误脱敏、聊天 raw HTML 禁令、模糊层 ≤5 和双缩放布局均无回归。
- 每阶段执行 `npm run typecheck`、`npm test`、`npm run build`；涉及 UI/打包时追加 portal/UI 探针、截图和真实应用冒烟。
